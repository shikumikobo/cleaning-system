## AI が決めた点（design.md の「決めたこと」に理由）

- 読み込みと確かめはブラウザの中で行い、Edge Function は作らない。書くのは RPC 1つ（`import_rows`）で、記録も同じ transaction で確定する
- 画面で確かめた行も、サーバーで検査と重なりをやり直す
- エラーの行があっても、取り込める行だけを取り込める。重なりは飛ばす（上書き・更新はしない）
- 取引先 → 建物 → 部屋 → 契約を、種類ごとに別のファイルで1回ずつ取り込む（名前で結びつける。同じ名前が2つあれば決まらないのでエラー）
- 契約は1行が清掃の中身1つ。（建物・種類・開始日・終了日）が同じ行を1つの契約にまとめ、1行でも間違いがあればその契約は全部取り込まない
- 契約の重なりは（建物・種類・開始日・清掃の名前の組）が同じもの
- 頻度は RRULE のほか、日本語の言い方も読む。締め日の「月末」・階の「2階」「3F」も受ける
- ファイルは保存しない（`import_jobs.file_path` は空）

## 新しい依存（apps/web）

- `read-excel-file`（.xlsx の読み込み。web-worker 版の入口を使う）
- `fflate`（ひな形の .xlsx の zip。`read-excel-file` が使っているものと同じ版）
- 理由：.xlsx は zip の XML で自作は危ない。`xlsx`（SheetJS）は npm の最終版に既知の脆弱性があるため選ばなかった

## 人の決定が要るもの

- なし（推奨の案で進めた）。次の2点は、運営者の目で見てほしい
  - エラーの行があっても取り込める行は取り込む、という扱い（1行の間違いで全部やり直しにしない形にした）
  - 重なりは「飛ばす」だけで、既存のデータを更新しない（更新が要るなら別の機能）

## 仕様と合わない点

- data-model.md の `import_jobs` の列は「kind、file_path、status、total_rows、error_rows」。実装は、これに `file_name`・`created_count`・`skipped_count`・`details` を足した（結果の画面と履歴のため）。`file_path` は置いたが空（ファイルを保存しないため）。data-model.md は直していない
- crud.md の 014 の行は「EF（確かめの画面で OK のあと、…RPC を呼ぶ）」。読み込みを画面（ブラウザ）で行うので EF は作らず、画面が RPC を呼ぶ形にした（課題4の「取り込んだ人の鍵で RPC」は守っている）
- 取り込んだ契約の履歴（`audit_logs`）の source は `rpc`（010 の `create_contract_import` が決める）。取引先・建物・部屋は `import`。010 の RPC は変えていない（`contracts.source = 'import'` で取り込みと分かる）
- `import_jobs.status` は `done`・`partial` の2つだけ（取り込みは1回の RPC で終わるため、途中の状態は持たない）
