# 機能003：案件（要件）

状態：実装
作成：2026-11-16

全体の言葉と役割は [../product.md](../product.md)、変えない決まりは [../constitution.md](../constitution.md)、表と policy の型は [../data-model.md](../data-model.md)（003 の章）、CRUD は [../crud.md](../crud.md)（003 の章）。001（会社・利用者・権限）・002（取引先・建物・部屋）・015（お知らせの仕組み）が前提。

## 1. ねらい

「あの建物の、この箇所を直してほしい」「共用部が汚れていた」といった、定期の清掃とは別に出てくる依頼・気づき・苦情を、案件として1か所に持つ。社員は電話やメールで受けた内容をスマホから短く登録し、期限と担当を決める。スタッフは現場の気づきから案件を起こし、自分の担当の案件だけを見て、状況を進める。期限が近い・過ぎた案件は警告し、担当者にお知らせする。案件の金額は別の表に分け、金額を見られる人だけが見る。請求書に載った金額は、あとから直せない。

## 2. 利用者の話

- 社員として、電話で受けた依頼を、建物・題名・期限だけでまず登録したい（あとから内容と担当を足す）
- 社員として、案件を状況（受付・対応中・完了・取消）・期限・建物・担当で絞り込み、期限切れと期限が近いものを先に見たい
- 社員として、案件に担当者（社員・スタッフ）を付けたい
- 社員として、案件に金額（請求する・しない）を付けたい。請求書に載ったあとは、金額が変わらないでほしい
- スタッフとして、現場で気づいたことを、建物を選んで短く案件にしたい（電波がない間は端末にためる。写真は 008 で付ける）
- スタッフとして、自分の担当の案件だけを見て、対応中・完了にしたい
- 担当者として、期限が近い・過ぎた案件のお知らせを受け取りたい
- 外部の人は、案件を見られない

## 3. 受け入れ基準

### 案件の登録と直し

- **R-003-1** `request.edit` を持つ人が、建物・依頼元の取引先・題名を入れて案件を登録したとき、システムは「受付」で保存する。内容・部屋・期限・担当・分類・入口は任意（分類の初めは「その他」、入口の初めは「手で登録」）
- **R-003-2** 題名が空・長すぎる（100字を超える）・分類や入口が決まった値以外・状況が「受付」以外で作ろうとする、ならば、システムは保存しない
- **R-003-3** 別の会社の取引先・建物・部屋・担当を指すならば、システムは案件を受け付けない。担当は、同じ会社の社内の人（外部の人でない）だけを選べる
- **R-003-4** `request.edit` を持つ人は、案件の中身（題名・内容・期限・担当・分類・部屋・建物・依頼元）を直せる。持たない人（スタッフ・外部の人・運営・ログインしていない人）は、案件を作れず、直せない
- **R-003-5** システムは、画面や API から直接、案件の状況（status）と `deleted_at` を書き換えさせない。状況の変更は RPC だけ。案件は消せない（取り消すだけ）
- **R-003-6** 案件を作る・直すとき、システムは履歴に残す（001 の変更の履歴）

### 読む

- **R-003-7** `request.edit` を持つ人（管理者・社員）には、会社の全員の案件を読ませる。スタッフには、担当が自分の案件だけを読ませる。外部の人・別の会社の人・運営（許可のない間）・ログインしていない人には、読ませない

### 状況の変更（RPC）

- **R-003-8** `request.edit` を持つ人が `set_request_status` を呼んだとき、システムは許された切り替えだけ行う：受付 → 対応中・完了・取消、対応中 → 受付・完了・取消、完了 → 対応中、取消 → 受付
- **R-003-9** 許されない切り替え（例：完了 → 取消、取消 → 完了）ならば、システムは状況を変えず、理由（`invalid_transition`）を返す。知らない状況の値ならば、断る
- **R-003-10** すでにその状況の案件に同じ状況を指定しても、システムは何も変えず、エラーにしない（二度呼んでも同じ）
- **R-003-11** 担当の案件のスタッフ（`field.record` を持つ人）が `set_request_status` を呼んだとき、システムは「受付 → 対応中」「受付 → 完了」「対応中 → 完了」だけを行う。取消・戻しは、`request.edit` を持つ人だけ。担当でない案件は、スタッフに切り替えさせない
- **R-003-12** 見つからない案件・別の会社の案件・権限のない人・ログインしていない人のとき、システムは同じエラー（42501）で断る（案件の存在を探らせない）
- **R-003-13** 請求書の明細に載った金額がある案件は、システムは取消にさせない（`billed` を返す）

### 気づきから案件を作る（RPC）

- **R-003-14** `field.record` を持つ人（スタッフを含む）が `create_request_from_observation` を呼んだとき、システムは、建物・題名（任意で内容・部屋・分類）から、入口「現場の気づき」・状況「受付」・担当は本人の案件を作る。依頼元は建物の依頼元を使う。作った人は、その案件を読める
- **R-003-15** 同じ端末の uuid で二度呼んでも、システムは案件を1件だけにし、二度目は前の結果を返す（電波のない間にためて送るため）。別の人・別の会社が作った uuid ならば、断る
- **R-003-16** `field.record` を持たない人（外部の人など）・別の会社の建物・消した建物・建物に属さない部屋のとき、システムは案件を作らない
- **R-003-17** 気づきの写真と案件のつなぎ（写真の側の `request_id`）は 008 が足す。003 では写真なしの案件を作るところまで

### 金額

- **R-003-18** `request.edit` と `amount.read` の両方を持つ人が、案件に金額（円の整数・0以上、請求する・しない）を付けたとき、システムは保存する。1つの案件に付く金額は、消していない行で1つだけ
- **R-003-19** `amount.read` を持たない人（スタッフ・外部の人）には、システムは案件の金額を読ませず、作らせず、直させない
- **R-003-20** 金額が負のとき、システムは保存しない（整数でない入力は、画面が送る前に断る。R-003-28）。別の会社の案件に付けることも、金額の行を別の案件へ付け替えることも、させない
- **R-003-21** 請求書の明細（`invoice_lines`）に載った案件の金額は、システムは直させず、消させない（論理削除も）。明細が取り消されて（`deleted_at` が入って）空いたら、また直せる。`invoice_lines` の表がまだない間は、常に直せる
- **R-003-22** 金額を作る・直す・消すとき、システムは履歴に残す

### 期限の警告とお知らせ

- **R-003-23** 期限（日本時間の日付）が今日より前の、受付・対応中の案件を「期限切れ」、今日から 3 日後まで（今日を含む）の受付・対応中の案件を「期限が近い」と判定する。完了・取消・期限なしの案件は警告しない。判定はシステムの1か所（画面の部品と定時の処理が同じ決まり）で行う
- **R-003-24** 定時の処理 `request_due_notify` を呼んだとき、システムは期限切れ・期限が近い案件の担当者に、種類 `request_due` のお知らせを「送る前」で作る。担当がいない（または止められている）案件は、`request.edit` を持つ有効な所属全員に作る。完了・取消・期限なし・期限が遠い案件には作らない
- **R-003-25** 同じ案件・同じ期限・同じ段階（近い・切れ）・同じ人には、システムはお知らせを二度作らない（何度呼んでも1件）。期限を直したあとや、近いから切れに変わったときは、新しく作る
- **R-003-26** 定時の処理は、会社ごとに分けて回し、処理の記録（`job_runs`、種類 `request_due`）を会社ごと・1回ごとに残す。ほかの会社の案件・所属には何も作らない。呼べるのは `service_role` だけで、ログインした利用者・anon は呼べない

### 一覧・絞り込み・画面

- **R-003-27** 案件の一覧は、状況・期限（期限切れ・近い・今週・期限なし）・建物・担当で絞り込め、並びは「期限切れ → 期限が近い → 期限が遠い → 期限なし」（同じ中では期限の早い順、次に新しい順）にする。完了・取消は、初めは一覧に出さない（絞り込みで出せる）
- **R-003-28** 案件の入力（題名・建物・依頼元・期限の日付・金額）は、保存の前に画面で検査する。DB の check と同じ決まり
- **R-003-29** 案件の一覧・登録・詳細・状況の変更を、スマホの幅で使える画面として持つ。金額の欄と操作は、`amount.read` を持つ人にだけ出す。スタッフには、登録の画面ではなく「気づきから案件を作る」形（建物・題名・内容）を出し、自分の担当の案件だけを一覧に出す。状況の操作は、その人に許された切り替えだけ出す（出さなくても DB が断る）

### 他のものとのつなぎ

- **R-003-30** 案件から使われている部屋は、システムは消さず「使わない」にする（002 の R-002-18。`app.usage_refs` の行が003の表の列名と合う）。終わっていない（受付・対応中の）案件のある建物は、システムは消さず、理由（`has_open_requests`）を返す
- **R-003-31** 別の会社の行ならば、システムは 003 の2つの表で、読ませず、作らせず、直させず、消させない（数も分からない）

- **R-003-32** `request.edit` を持つ人が呼んだとき、システムは、担当に選べる人（同じ会社の有効な社内の所属。外部の人を除く）の所属の ID・表示名・役割を返す。持たない人・別の会社の人・ログインしていない人には返さない（所属の表は管理者だけが読めるため、案件の画面のために別に出す）

## 4. 範囲の外

- 写真の受け取りと、写真と案件のつなぎ（008）。見積から案件を引く・案件から作業を作る（004・012）
- 請求書への明細の取り込み（011。`invoice_lines` を作る側）
- 案件の担当の通知（割り当てたときのお知らせ）。種類 `request_due` だけを使う
- 定時の処理を動かす設定（配備側のスケジューラ。Edge Function と DB の関数まで作る）

## 5. 決まっていないこと（推奨の案で進める）

| 点 | 推奨 | 理由 |
|---|---|---|
| 状況の値 | `new`・`in_progress`・`done`・`cancelled` | 日本語の「受付・対応中・完了・取消」をコードの値にした（002 と同じ） |
| 分類 | `cleaning`（清掃）・`repair`（修繕）・`complaint`（苦情）・`inquiry`（問い合わせ）・`other` | 清掃業で最初に出る型。足すときは check を直す |
| 入口 | `manual`・`phone`・`email`・`field`・`import` | 手・電話・メール・現場の気づき・014 の取り込み |
| 期限が「近い」の日数 | 3 日 | 週末をまたぐ前に気づける。定時の処理の引数で変えられる |
| 完了・取消の案件の期限 | 警告しない | 終わったものを警告しても、ノイズになる |
