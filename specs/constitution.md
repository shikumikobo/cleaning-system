# 原則（cleaning：清掃業のシステム）

どの機能でも変えない決まり。変えるときは、人の OK をもらってから直す。機能ごとの中身は `NNN-*/`、全体は [product.md](product.md)。

## 1. 構成

| 役割 | 使うもの |
|---|---|
| 画面 | Next.js（App Router、静的な書き出し）・React・TypeScript。スマホのホーム画面に置ける形（PWA） |
| 公開の先 | Cloudflare Pages（試しはプレビュー、本番は main） |
| DB・ログイン・ファイル | Supabase（東京のリージョン）。PostgreSQL・Auth・Storage |
| サーバーの処理 | Supabase Edge Functions（招待、期限つきのファイルの URL、定期の処理、決済の知らせ） |
| コード | GitHub の非公開のリポジトリ（shikumikobo）。パッケージは pnpm |
| 配る | GitHub Actions。DB の変更（マイグレーション）→ 画面の公開の順。会員制の環境と、受託のお客さんの環境に、同じ版を順番に配る |

- 環境は、ローカル（`supabase start`）・試し・本番の3つ。DB の形は、マイグレーションのファイルでだけ変える（管理の画面で直接変えない）
- キー・パスワードは、Cloudflare と Supabase の設定の画面と、GitHub の Secrets にだけ入れる。コード・仕様・メッセージに書かない
- **受け持つ場所を分ける**。権限は DB が守るので、画面での出し分けは見せ方のためだけ

| 受け持つ場所 | 受け持つこと | 例 |
|---|---|---|
| DB の制約と RLS | 壊れたデータを入れない。見えてはいけないものを見せない | 会社をまたがない、一意、check、権限 |
| DB の関数（RPC） | いくつかの表をまとめて変える操作と、状況の切り替え。1つの操作に1つの関数 | 見積の提出・承認、請求書の発行・取り消し、番号の発行、合計の確定、契約の変更、建物の削除 |
| Edge Function（TypeScript） | 外とのやりとりと、重い処理・定時の処理 | 予定の作成、お知らせ、メール、決済、住所から位置、レシートの読み取り、取り込みのファイル、古いデータとファイルの掃除 |
| 画面 | 入力の確かめと見せ方。1つの表だけを変える簡単な登録・編集は、画面から直接書く | 下書きの間の合計の表示、取引先・建物の登録 |

  - 画面は status を直接書き換えない（状況の切り替えは RPC だけ）
  - トリガーは、変更の履歴と `updated_at` だけに使う。業務の決まりはトリガーに書かない
  - 同じ計算（税・合計）を画面と DB の両方に書くときは、同じテストのデータで結果が合うことを確かめる。正は DB
- **電波がなくても現場の記録はできる**：現場の写真・清掃報告書・作業の開始と終了は、電波がないときは端末の中にため、電波が戻ったら自動で送る。送れていない件数を画面に出し、送れるまで端末から消さない。同じ記録を二度送っても1件になるようにする（記録ごとに端末で ID を作る。後でまとめて呼ぶ RPC も、この ID で二度目は何もしない）

## 2. データの分け方と権限

- **会社（テナント）で分ける**：業務の表はすべて `tenant_id` を持つ。RLS は「自分が所属する会社の行だけ」。別の会社の行は、読めない・書けない・数も分からない
- **すべての表で RLS を ON**。何も決めていない操作は拒否される形にする（許すものだけ policy を書く）
- 権限の判定は、権限の表（役割 × 権限）と1つの判定の関数に集める。policy に役割の名前を直接書かない
- policy は、表を少しの型に分けて、型ごとに同じ形で付ける（[data-model.md](data-model.md) の4章）。表ごとに手で書き分けない。DB のテストも型ごとに同じものを、すべての表に流す
- サービスの運営（しくみ工房）も、会社のデータは普段は読めない。運営は会社の所属を持たず、問い合わせで見るのは、会社の管理者が期限つきで許した間だけ（読むだけ。[data-model.md](data-model.md) の `support_access_grants`）
- **消さない**：業務のデータは論理削除（`deleted_at`）。変更の履歴（だれが・いつ・何を・前と後）を DB のトリガーで残す。画面から履歴は書き換えられない。現場の記録（写真・報告書など、数の多い表）は履歴を付けず、作った時刻・届いた時刻・版の番号で追う
- ファイルは非公開の置き場所に、`<tenant_id>/…` の頭で置く。見せるときは期限つきの URL
- 個人の情報は、業務に要る分だけ持つ。入居者の名前は持たず、部屋番号までにする
- 金額は円の整数。消費税は帳票ごとに1回かけ、端数は切り捨て。日時は日本の時刻（Asia/Tokyo）で見せる

## 3. テストと確認

- 受け入れ基準（`R-NNN-n`）ごとに1つ以上のテスト。テストの名前に基準の番号を入れる
- 権限とデータの分け方は、DB のテスト（`supabase/tests/` の pgTAP）で、役割ごと・会社ごとに確かめる。「見えてはいけないものが見えない」を必ず入れる
- 計算や変換は単体のテスト（Vitest）。画面の流れは Node 版の Playwright
- CI（GitHub Actions）で、lint・型・単体・DB のテスト・ビルド・`spec.py check cleaning --strict` を通す。通らないものは配らない
- テストと見本に使うデータは架空のもの。実在の会社・人・建物の名前を使わない

## 4. 書かないもの

- 実作業の時間と、お客さんに実際に請求した金額（仕様・コード・コミット・画面のどこにも）
- 受託の案件のお客さんの情報（名前・数字・やりとり）。必要な考え方だけを、一般の言葉で書く
- 運営者の本名につながること
