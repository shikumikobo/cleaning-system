# 機能004：見積（要件）

状態：実装
作成：2026-11-17

全体の言葉と役割は [../product.md](../product.md)、変えない決まりは [../constitution.md](../constitution.md)、表と policy の型は [../data-model.md](../data-model.md)（004 の章、型 B＋D）、CRUD は [../crud.md](../crud.md)（004 の章）。001（権限・番号）・002（取引先・建物）・015（お知らせ）が前提。

## 1. ねらい

見積書づくりの手間を減らす。取引先と建物を選び、品名の候補から明細を入れて、合計と税を自動で出し、A4 の見積書として印刷（PDF は画面の印刷）する。案件がなくても作れる。定期の清掃は「基本の月額」と「オプション（頻度つき）」で見積もる。提出した見積は、あとから直せない（直すときは新しい版を作る）。取引先から返事をもらったら、社員が「承認」か「不成立」を記録する。承認は、後の機能（010 契約・011 請求）の元になる。

## 2. 利用者の話

- 社員として、取引先と建物を選び、品名の候補から明細を入れて見積書を作りたい。案件がなくても作りたい
- 社員として、定期の清掃を「基本の月額」と「オプション（毎月第2火曜・3か月に1回 など）」で見積もりたい。頻度は日本語で読めてほしい
- 社員として、提出したら番号が付き、数字が固定されてほしい。直すときは新しい版にしたい
- 社員として、取引先の返事を「承認」か「不成立」で記録したい。承認したら、社内の関係者に知らせたい
- 社員として、見積書を A4 で印刷したい。会社の名前・住所・インボイスの登録番号が載ってほしい
- 管理会社の担当者（外部）として、自分に許された建物の、提出された見積だけを見たい
- スタッフは、金額と見積を見ない

## 3. 受け入れ基準

### 品名の候補

- **R-004-1** `quote.edit` を持つ人が品名の候補（名前・単位・単価・種類：基本／オプション／単発）を登録したとき、システムはそれを保存する。名前が空・単価が負・種類が決まった値以外ならば、保存しない。同じ名前（消していない行）は2つ作らない
- **R-004-2** 品名の候補を直す・消す（論理削除）とき、システムはそれを保存する。すでに見積の明細に写した品名と単価は、変えない

### 見積（下書き）

- **R-004-3** 社員が取引先と建物を選んで見積（種類：案件・定期・特別清掃）を作ったとき、システムは下書きとして保存する。案件（`request_id`）は空でもよい。別の会社の取引先・建物ならば、システムは受け付けない
- **R-004-4** 社員が下書きの見積の明細（種類：基本・オプション・単発、品名、数量、単位、単価）を足す・直す・消すとき、システムはそれを保存する。金額は、システムが 数量 × 単価（円未満は四捨五入）で出す。数量が 0 以下・単価が負・名前が空ならば、保存しない
- **R-004-5** 明細の繰り返し（`recurrence`）が RRULE の文字列の形でないならば、システムは保存しない
- **R-004-6** 画面や API から直接、状況・番号・発行日・合計・税・決めた人と日・元の版（`previous_id`）を書き込むならば、システムはそれを受け付けない（これらは RPC だけが決める）
- **R-004-7** 社員が下書きの見積を消す（論理削除）とき、システムはそれを保存する。提出したあとの見積は、システムは消させない

### 提出

- **R-004-8** 社員が下書きの見積を提出したとき、システムは、明細の金額の合計（小計）・税・合計を計算して入れ、番号と発行日（日本時間の今日）を付け、状況を「提出」にする。有効期限が空ならば、発行日の 30 日後を入れる
- **R-004-9** 税は、帳票ごとに1回、小計 × 税率で出し、円未満を切り捨てる。合計は 小計 ＋ 税。明細ごとには税をかけない
- **R-004-10** 番号は `Q-<西暦>-<4桁の通し番号>`（例 Q-2026-0001）で、会社ごと・年ごとに 1 から振る。同じ番号を2通に付けず、欠番を作らない（提出に失敗したら、番号も進まない）
- **R-004-11** 明細が1つもない見積は、システムは提出させない。有効期限が発行日より前の見積も、提出させない
- **R-004-12** 種類が「定期」の見積は、基本の明細が1つ以上あり、基本とオプションのすべてに繰り返しがあるときだけ提出できる。「定期」でない見積は、明細に繰り返しがあれば提出させない
- **R-004-13** すでに提出した見積を、もう一度提出したとき、システムは何もしないで、前の番号と合計を返す（二重に番号を振らない）
- **R-004-14** 提出した見積と、その明細は、システムは直せない・消せない・足せない（RLS で止める。状況が下書きの行だけ直せる）

### 承認・不成立

- **R-004-15** 社員が、提出した見積を承認したとき、システムは状況を「承認」にし、決めた日時と人を記録する。提出していない見積・不成立の見積は、承認させない。承認を二度呼んでも、同じ結果で終わる
- **R-004-16** 社員が、提出した見積を不成立にしたとき（理由は任意）、システムは状況を「不成立」にし、決めた日時・人・理由を記録する。下書き・承認済みは、不成立にさせない
- **R-004-17** 見積を承認したとき、システムは、金額を見られる所属（`amount.read`。承認した本人を除く）に、お知らせ（種類 `quote_approved`）を「送る前」で作る。同じ見積の承認で二通は作らない。不成立ではお知らせを作らない
- **R-004-18** 承認・不成立にしたあとの見積は、システムは直させず、状況も戻させない

### 直す（新しい版）

- **R-004-19** 社員が提出済み・不成立の見積から「直す」を呼んだとき、システムは、元の版を `previous_id` に入れた新しい下書き（明細も写す。番号はなし）を作る。承認済みの見積からは作らせない。同じ元からの直しの下書きは1つだけ（もう一度呼ぶと、その下書きを返す）
- **R-004-20** 直した版を提出したとき、元の版が「提出」のままなら、システムは元の版を「不成立」（理由：改訂版に置き換え）にする。同時に有効な見積が2つにならないようにするため

### 権限と守り

- **R-004-21** スタッフ・外部の人・運営・ログインしていない人ならば、システムは見積・明細・品名の候補を作らせず、直させず、RPC（提出・承認・不成立・直す）も呼ばせない。社員・管理者は、すべてできる
- **R-004-22** `amount.read` を持たない人（スタッフ）ならば、システムは見積・明細・品名の候補を読ませない
- **R-004-23** 外部の人ならば、システムは、許された建物の、提出・承認の見積とその明細だけを読ませる。下書き・不成立・許されていない建物の見積と、品名の候補は読ませない。外部の人は書けない
- **R-004-24** 別の会社の見積・明細・品名の候補は、読めない・直せない・RPC も効かない（RPC は、行が見つからないときと権限がないときを、同じ 42501 で返す）
- **R-004-25** 見積・明細・品名の候補を作る・直す・消すとき、システムは履歴に残す（001 の変更の履歴。RPC の変更は source が rpc）
- **R-004-26** 取引先・建物に、消していない見積があるならば、システムはその取引先・建物を消さず、理由（`has_quotes` と件数）を返す（`app.usage_refs` に登録する）

### 繰り返し（定期の見積）

- **R-004-27** 繰り返しの RRULE を、システムは日本語に訳して見せる（例：`FREQ=MONTHLY;BYDAY=2TU` → 「毎月 第2火曜」、`FREQ=WEEKLY;BYDAY=MO,TH` → 「毎週 月曜・木曜」、`FREQ=MONTHLY;INTERVAL=3` → 「3か月に1回」、`FREQ=MONTHLY;BYMONTHDAY=-1` → 「毎月 月末」）。読めない形のときは、元の文字列をそのまま見せる
- **R-004-28** 画面で選んだ頻度（毎週◯曜・毎月第◯◯曜・毎月◯日・◯か月に1回）から、システムは RRULE の文字列を作る。作った文字列を訳すと、選んだ頻度に戻る

### 合計・印刷

- **R-004-29** 画面の下書きの合計（小計・税・合計）は、DB の提出の RPC が出す合計と、同じテストのデータ（`supabase/tests/fixtures/quote_totals.json`）で、すべて一致する
- **R-004-30** 見積書は、画面の印刷で A4 に出す。見積書には、見積の番号・発行日・有効期限・宛先（取引先と建物）・明細（品名・数量・単位・単価・金額・頻度）・小計・税（税率つき）・合計・会社の名前・住所・電話・インボイスの登録番号を載せる。登録番号が未登録ならば、その行は出さない。下書きは「下書き」と分かる印を付ける
- **R-004-31** 見積の一覧・作成・明細の編集（下書きの間）・提出・承認・不成立・直す・印刷、品名の候補の管理を、スマホの幅で使える画面で持つ。提出していない見積の合計は、画面で計算して見せる。入力は保存の前に検査し、提出できない理由（R-004-11・12）は日本語で出す

## 4. 範囲の外

- 外部の人が専用ページで承認を押す形（005 の design で決める。いまは社員が記録する）
- 案件の表（003）との外部キー（`quotes.request_id` は列だけ。003 の取り込みのあとで足す）
- 承認された見積から契約を作る処理（010）
- 見積の PDF のファイル保存・メール送付（PDF は画面の印刷。メールは範囲の外）
- 外部の人が、見積を作った人の名前を見る仕組み（001 の `app.can_see_profile` を直す必要があり、009 と一緒に決める）
- 値引きの行（マイナスの単価）。軽減税率（帳票の中で税率が混ざること）

## 5. 決まっていないこと（推奨の案で進める）

| 点 | 推奨 | 理由 |
|---|---|---|
| 見積番号の形 | `Q-<西暦>-<4桁>` | 会社ごと・年ごとの通し番号（data-model.md の `document_counters`）。ひと目で見積と分かる |
| 有効期限が空のとき | 発行日の 30 日後 | 見積書に有効期限がないと、取引先に伝わらない |
| 定期の見積の合計 | 明細の金額の単純な合計（基本の月額＋オプションの1回分＋単発）に税をかける。頻度は明細に載せる | 期間ごとの総額は、契約（010）が決める。ここでは1枚の見積書としての合計だけを持つ |
| 建物 | 見積に必須（外部の人に見せる条件が建物のため） | 建物をまたぐ見積は、建物ごとに分けて作る |
| 直した版を提出したときの元の版 | 「不成立」（理由つき）にする | 有効な見積が1つだけになる。状況の値を増やさない |
| 税率の持ち方 | 帳票ごとに小数（初めは 0.10）。画面は % | 税率が変わっても、出した帳票は変わらない |
