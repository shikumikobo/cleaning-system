# 機能009：清掃報告書（要件）

状態：実装
作成：2026-11-20

全体の言葉と役割は [../product.md](../product.md)、変えない決まりは [../constitution.md](../constitution.md)、表と policy の型は [../data-model.md](../data-model.md)（008・009・012 の章）、CRUD は [../crud.md](../crud.md)（009 の章）。001（権限・履歴）・002（建物・場所）・005（専用ページの区画の登録簿）・008（写真）・010（作業・担当）が前提。

## 1. ねらい

建物ごとに「報告のひな形」（チェックする項目）を持ち、スタッフが現場のスマホで、作業ごとに報告書（項目のチェック・メモ・写真の前と後・気づき）を作る。電波がなくても作れて、戻ったら送られる。社員が確認し、提出すると、外部の人（管理会社など）が専用ページで読める。提出・確認のあとは固定される。PDF は画面の印刷で作る。

## 2. 利用者の話

- 管理者・社員として、建物ごとに報告のひな形（項目の並び）を作り、場所を付け、使わない項目は「使わない」にしたい
- スタッフとして、作業を開くと、ひな形の項目が並んだ報告書がすぐ作れて、チェックとメモと前後の写真を入れたい。電波がなくても失いたくない。同じ作業の担当の2人で、同じ報告書を作りたい
- 社員として、スタッフが作った報告書を確認し、直してほしいときは下書きに戻し、よければ提出したい
- 外部の人として、提出された報告書と写真だけを、専用ページで読みたい（下書きや確認中のものは見たくない）
- 社員として、報告書を画面の印刷で PDF にしたい
- 提出・確認のあとの報告書と写真は、だれも書き換えられない

## 3. 受け入れ基準

### ひな形と項目

- **R-009-1** `master.edit` を持つ人が、建物を選んでひな形（名前）を作り、名前と「使う・使わない」を直せる。名前が空（空白だけを含む）・別の会社の建物ならば、システムは保存しない。同じ建物で同じ名前の（消していない）ひな形は2つ作れない
- **R-009-2** `master.edit` を持つ人が、ひな形の項目（名前・場所・並び順）を作り、直せる。名前が空・別の会社のひな形や場所・ひな形の建物と違う建物の場所を指すならば、システムは保存しない。場所は付けなくてもよい
- **R-009-3** ひな形と項目は、会社の中の人（スタッフを含む）が読める。`master.edit` を持たない人（スタッフ）は作れず・直せない。外部の人は読めない
- **R-009-4** ひな形を消す RPC（`delete_report_template`）：`master.edit` を持つ人だけが呼べる。作業か契約の中身が使っていれば、消さずに「使わない」にして、理由を返す。使っていなければ、項目も一緒に論理削除する。二度目は何もしない。別の会社・存在しないは、権限がないのと同じ 42501
- **R-009-5** ひな形の項目を消す RPC（`delete_template_item`）：`master.edit` を持つ人だけが呼べる。報告書の項目に写されていれば、消さずに「使わない」にして理由を返す。写されていなければ論理削除する
- **R-009-6** `works.report_template_id`・`contract_services.report_template_id` は、`(tenant_id, id)` の組で `report_templates` を指す外部キーを持つ。別の会社・存在しないひな形は指せず、空は許す
- **R-009-7** 建物を消すと、その建物のひな形と項目も一緒に論理削除される。ひな形の項目から使われている場所は、消さずに「使わない」になる（002 の登録）

### 報告書の行

- **R-009-8** `field.record` を持つ人が、自分が担当の作業の報告書の行（状況は下書き）を作れる。担当でない人・担当を外された人・別の会社の人・外部の人・どこにも属さない人は作れない。別の会社の作業・ひな形は指せない
- **R-009-9** 報告書は、状況が下書きで、確認・提出の列が空のものだけを作れる。確認済み・提出で作る、確認や提出の人・時刻を入れて作ることは、システムは断る
- **R-009-10** 同じ uuid の報告書は1件だけ（端末の送り直し＝既にあれば無視する書き方で、二度送っても増えない）。同じ作業に、別の uuid の報告書を2つ作ることは、システムは断る（消していない行で一意）
- **R-009-11** 下書きの間だけ、担当の全員が、報告書のメモ（remarks）と版（version）を直せる。作業・ひな形・状況・確認や提出の列は直接は直せない。報告書の行は消せない（delete も論理削除もできない）
- **R-009-12** 報告書を読めるのは、その作業の担当の全員と `work.assign` を持つ人。担当でないスタッフ・別の会社の人は読めず、数も分からない
- **R-009-13** 報告書の項目の行（名前・場所・並び順・チェック・メモ）を、担当が作り、チェックとメモを直せる（下書きの間だけ）。名前が空・別の報告書や別の会社を指す・ひな形の項目が別の会社ならば、システムは保存しない。同じ uuid は1件だけ。名前・場所・並び順・報告書は直せない
- **R-009-14** 確認の RPC（`check_report`）：`work.assign` を持つ人だけが呼べる。下書きを「確認済み」にし、確認した人（所属）と時刻と版の増えを残す。二度目は何もしないで前の結果を返す。提出済みなら理由を返す。スタッフ・外部の人・別の会社の人・ログインしていない人は 42501
- **R-009-15** 提出の RPC（`submit_report`）：`work.assign` を持つ人だけが呼べる。確認済みを「提出」にし、提出した人と時刻を残す。下書きのままの提出は、理由を返して断る。二度目は何もしない
- **R-009-16** 差し戻しの RPC（`reopen_report`）：`work.assign` を持つ人だけが呼べる。確認済みを下書きに戻し、確認の人・時刻を消す。提出済みは戻せない（理由を返す）
- **R-009-17** 確認済み・提出のあと、報告書は固定される。担当は、報告書のメモ・項目のチェックとメモを直せず、項目を足せず、その項目の写真を足せず・直せず・消せない（読める）。直接書き換えられるのは下書きの間だけ。状況は RPC だけが変える
- **R-009-18** 確認・差し戻し・提出のたびに、版（version）が1つ上がる

### 外部の人

- **R-009-19** 外部の人が読める報告書と項目は、提出済みで、許された建物の作業のものだけ。下書き・確認済み・許されていない建物・別の会社のものは読めない。外部の人は、報告書・項目を作れず・直せない
- **R-009-20** 外部の人が読める写真は、提出済みの報告書の項目につながる、許された建物の写真だけ（`app.photo_external_visible` の本物）。下書きや確認済みの報告書の写真、項目につかない写真（気づき）、許されていない建物の写真は読めない
- **R-009-21** 外部の人は、確認・提出・差し戻し・ひな形を消す RPC を呼べない
- **R-009-22** 別の会社の報告書・項目・ひな形・項目は、どの役割からも読めず・直せず・数も分からない（全部の表の漏れの確かめに入る）
- **R-009-23** `photos.report_item_id` は、`(tenant_id, report_item_id)` の組で報告書の項目を指す外部キーを持つ。別の会社・存在しない項目は指せず、空は許す。写真の固定の判定（`app.photo_report_locked`）は、項目の報告書が下書きでないとき真

### 端末（下書きの組み立てと、ためて送る）

- **R-009-24** 下書きの組み立て：作業のひな形の、使う項目（「使わない」を除く）を、並び順どおりに、項目の行として写す（名前・場所・ひな形の項目を持ち、チェックは外れ、メモは空）。各行の uuid と報告書の uuid は端末で作る。ひな形がない・使う項目が1つもないときは、項目「清掃全体」を1つ作る（写真の付け先になる）。報告書の元のひな形は、作業が写した ID を使う
- **R-009-25** 端末の入れ物（IndexedDB）に、報告書ごとに1件ためる。同じ報告書の id は1件（保存し直すと中身を置き換える）。送れるまで消さない
- **R-009-26** 送る順は、報告書 → 項目（既にあれば無視する書き方）→ チェックとメモ → 報告書のメモ。成功したら端末から消す。二度送っても、サーバーの行は増えない。電波がない・ログインが切れていれば、止めて残す（エラーにしない）。同時に2回呼んでも1回だけ動く
- **R-009-27** サーバーに断られた（権限・固定のあと・同じ作業の報告書がほかの端末で作られていた）ものは、端末に残し、理由を覚え、次へ進む。人が選んで、あきらめて端末から消せる
- **R-009-28** 報告書のメモを送るとき、版を条件にする。版が食い違い、サーバーのメモが自分のものと違うときは、「ほかの人が直しています」で残す。サーバーのメモが自分のものと同じなら、送れたことにする
- **R-009-29** 写真の端末の入れ物は、報告書の項目つきの写真を送るとき、項目の行がサーバーにまだなければ、断られた扱いにせず待つ（残して、あとで送る）。写真の行は、作業・報告書の項目・撮った種類（前・後・気づき）を持つ

### 画面

- **R-009-30** 状況の表記（下書き・確認済み・提出）と、進み具合（チェック済みの数 / 項目の数）の表記が決まっている。固定のあと（確認済み・提出）は、報告書の画面で直せない
- **R-009-31** 一覧（`/reports/`）：スタッフは自分が担当の作業（最近のもの）を、報告書の状況つきで見る。`work.assign` を持つ人は、全員の作業と、確認待ちの報告書を見る。作業から報告書を開く・作る
- **R-009-32** 報告書の画面（`/reports/edit/`）：項目ごとにチェックとメモを入れ、前・後の写真を撮れる。報告書全体のメモ・気づき（写真）も入れる。保存すると端末にためて送る。固定された報告書は読むだけ。電波がないときは、端末にためた件数を出す
- **R-009-33** 確認・提出の画面（`/reports/review/`）：`work.assign` を持つ人が、報告書の中身と写真を見て、確認・差し戻し・提出ができる。押せるボタンは状況で決まる（判定は DB）
- **R-009-34** 印刷の画面（`/reports/print/`）：建物・日・項目と結果・メモ・写真を、印刷に向いた並びで出す。画面の印刷で PDF にできる（印刷のときは操作のボタンを隠す）
- **R-009-35** ひな形の編集の画面（`/reports/templates/`）：建物を選び、ひな形と項目を作る・名前を直す・並べ替える・「使わない」にする・消す。編集を出すのは `master.edit` を持つ人だけ（判定は DB）
- **R-009-36** 専用ページ（005）の区画の登録簿に、報告書の区画と写真の区画が入る（同じ id なら置き換わる）。区画は建物の ID だけで中身を取る：提出した報告書（作業の日・項目と結果・メモ）と、その写真（押すと期限つきの URL で開く）
- **R-009-37** ホームに「清掃報告書」のリンクがある。「出ていない報告書」のお知らせは 015 の `report_missing`（既にある）を使い、波 6 で足す

## 4. この機能に含めないこと

- 「出ていない報告書」のお知らせを作る処理（波 6。種類 `report_missing` は 015 にある）
- 作業の担当の割り当て・開始と終了・状況の切り替え（012）
- 外部の人に見せる「確認した人の名前」（`profiles` の外部向けの読み取り。決まっていないため、見せない）
- 写真の撮り方・縮小・端末の入れ物の基本（008。ここは報告書の項目に付ける列と順番だけ足す）

## 5. 人の確認が要ること

- 提出の流れ（スタッフが作る → 社員が確認 → 社員が提出。提出は確認のあとだけ。確認を省く短縮はない）と、差し戻し（確認済みから下書きへ）を足したこと（design.md の「決めたこと」）
