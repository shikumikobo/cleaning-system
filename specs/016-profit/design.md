# 機能016：売上と粗利（設計）

要件は [requirements.md](requirements.md)。表と policy の型は [../data-model.md](../data-model.md)（016 の行）が正で、ここは 016 での実際の形を書く。policy の付け方は [../001-tenants-users/design.md](../001-tenants-users/design.md) の `app.apply_policy`、使われ方の登録は [../002-clients-buildings/design.md](../002-clients-buildings/design.md) の `app.usage_refs`、売上の元は [../011-invoices/design.md](../011-invoices/design.md)、小口は [../006-petty-cash/design.md](../006-petty-cash/design.md)、契約・作業は [../010-contracts/design.md](../010-contracts/design.md)。

## 1. 表と view

新しい表は `costs` だけ（data-model.md のとおり）。売上と小口は、すでにある表を view で集める（表は増やさない）。

| もの | 型 | 列・中身 | 基準 |
|---|---|---|---|
| `costs` 費用 | B | month（月の1日。check）、building_id・contract_id（どちらも空でよい。組の外部キー）、kind（`outsourcing`・`material`・`other`）、amount（bigint、1 以上 1000 億以下）、note | R-016-5・9〜12 |
| view `profit_lines` | ― | 1件ごとの金額：tenant_id、month、client_id、building_id、contract_id、kind（`revenue`・`draft`・`petty`・`outsourcing`・`material`・`other`）、amount | R-016-1〜5 |
| view `profit_monthly` | ― | `profit_lines` を 月×取引先×建物×契約 で集めた行：revenue・draft_revenue・petty・outsourcing・material・other_cost・gross | R-016-6・7 |

共通の列（`id`・`tenant_id`・作成と更新の人と時刻・`deleted_at`）と `unique (tenant_id, id)` は、data-model.md の1章のとおり。

- 012（作業の予定と実績）の表への外部キーは付けていない。費用は作業に付けない（要件の範囲の外）ので、列も置いていない
- 建物と契約の両方を指す費用は、契約の建物と同じでなければならない。判定は `app.cost_refs_ok`（security definer・`search_path` 固定）を、policy の `with check` から呼ぶ。別の会社の建物・契約は、組の外部キーが止める（`23503`）

## 2. 権限（RLS）

| 対象 | 読める人 | 書ける人 |
|---|---|---|
| `costs` | `amount.read`（運営は許可の間） | `invoice.edit`。作る・直す・消す（`deleted_at`）。建物と契約が合わない行は書けない（`42501`） |
| `profit_lines`・`profit_monthly` | 見る人の権限で絞る（`security_invoker`）。`anon` には権限を渡さない | ― |

- policy は `app.apply_policy('public.costs', 'B', {"write_perm": "invoice.edit"})` から作り、insert・update の policy だけを、建物と契約の確かめを足して作り直した（006 の出入りと同じやり方）。履歴は型 B の既定で付く
- **view の守り**：view は、請求書・明細・契約・契約の中身・作業・案件・建物・小口・費用を読む。どれも見る人の RLS を通るので、スタッフ・外部の人・別の会社の人は、請求書と明細の RLS で 0 行になる。ただし小口の出入りは**持ち手の本人も読める**ので、スタッフが自分の出金を粗利に足して見られないよう、小口の枝に `public.has_perm(tenant_id, 'amount.read')` を付けた（R-016-14）
- 名前を引くために読む建物（型 A）・作業（型 A。担当の作業だけの人もいる）は、`amount.read` だけで `work.assign` のない役割だと、引けずに「建物なし」に入ることがある。初めの役割（管理者・社員）は全部持っているので起きない。起きても数字は消えず、「建物なし」の行に入る（R-016-7）

## 3. 集計の決め方

### 売上（R-016-1〜3）

`invoice_lines` の消していない明細の `amount`（税抜）。請求書は消していない、状況が `issued`・`sent`・`partial`・`paid`。月は請求書の `period`（請求月）。状況が `draft` の請求書の明細は `kind = 'draft'`（売上とは別の列）。取消・消した請求書、外した明細は入らない。

建物と契約は、明細の元から決める。

| 明細の元 | 契約 | 建物 |
|---|---|---|
| 契約の中身（`service_key`） | その鍵の契約の中身（行が複数あっても、どれも同じ契約。新しい行を使う）から契約 | 契約の建物 |
| 作業（`work_id`） | 契約の作業なら、その契約の中身から契約。案件の作業は空 | 作業の建物 |
| 案件（`request_id`） | 空 | 案件の建物 |

取引先は、どの元でも請求書の取引先。

### 費用（R-016-4・5）

- **小口**：`cash_entries` の `direction = 'out'` で、状況が `confirmed`・`closed`、消していないもの。月は出金の日（`entry_date`）の月。建物は、出入りの建物、なければ作業（`work_id`）の建物。契約は、作業が契約の作業のときだけ。取引先は、建物の取引先。小口の金額は入力したまま（税込のことが多い）
- **手で入れた費用**：`costs` の消していない行。建物が空で契約があれば、契約の建物。取引先は、建物の取引先。建物も契約も空なら、取引先・建物・契約のない「共通」の行

### 粗利（R-016-6）

粗利 ＝ 売上 − 小口 − 外注 − 材料 − その他。下書きは入れない。`profit_monthly` の `gross` に入っている（列を足し引きして出す）。1行（月×取引先×建物×契約）の中で、売上のない行（費用だけ）は粗利がマイナスになる。画面は、契約・建物・取引先のどれで集めても、全体の合計が変わらないように、行を足し合わせる（R-016-7）。

## 4. 速さ（R-016-18）

月の集計は、`tenant_id = ? and month = ?`（比べるときは `month in (?, ?, ?)`）で読む。view は条件を中の表まで渡せる形（集める列は、グループの列と同じ）にしてあり、それぞれ次の索引を使う。

| 元 | 索引 | 理由 |
|---|---|---|
| 請求書 | `invoices_period_idx (tenant_id, period) where deleted_at is null`（新しく足した） | 011 の索引は状況が先頭で、月だけでは使えない。請求月で絞るため。明細は、その請求書の `invoice_lines_invoice_idx (tenant_id, invoice_id, sort)` で引く |
| 小口 | `cash_entries_out_month_idx (tenant_id, (月の1日に直した出金の日)) where deleted_at is null and direction = 'out'`（新しく足した） | 006 の索引は持ち手が先頭。月は view の `month` と同じ式にして、索引に使えるようにした（`timestamp` にしてから直すので、索引の式にできる） |
| 費用 | `costs_month_idx (tenant_id, month) where deleted_at is null` | 月で絞るため。消した行は索引に入れない |
| 契約の中身 | 010 の `contract_services_key_idx (tenant_id, service_key, valid_from)` | 明細の鍵から契約を引く（行ごとに1回の索引引き） |

- 名前を引く表（建物・契約・作業・案件）は、主キーか `(tenant_id, id)` の一意の索引で引く
- テスト（R-016-18）は、36 か月 × 60 取引先の請求書・明細、小口 3000 件、費用 1500 件を足し、統計を取ってから、`tenant_id` と `month` で読んだ計画に、3つの索引の名前が出て、請求書・小口・費用の全表の走査がないことを確かめる。**この規模だと、明細の表は、請求書の ID での結合を、ハッシュ結合（全部を一度読む）で解いている**。表が大きくなれば、請求書の ID から索引で引く形に変わる見込み（推測。大きいデータでの実測は、まだしていない）
- 遅くなったとき（data-model.md）は、前の月までを毎晩の集計の表にする。それまでは、view のままにする

## 5. 使われているものは消さない

002 の `app.usage_refs` に、建物の `costs`（`building_id = $2`、理由 `has_costs`、止める）を足した。費用が1件でも（消していないもの）入っている建物は、消せない（費用を消せば消せる）。契約だけを指す費用（建物は空）は、止めない（建物を直接指していないため）。画面の文面（`has_costs`）は、`lib/masters/format.ts` に1行足した。

## 6. 画面

`apps/web/src/app/profit/`。静的書き出しに合うよう、パスは固定。スマホの幅で使える。

| 画面 | パス | 主な操作 | 基準 |
|---|---|---|---|
| 売上と粗利 | `/profit/` | 月を選ぶ。契約ごと・建物ごと・取引先ごとに集める。月の合計（売上・費用・粗利・粗利率・費用の中身・下書きの分）。前の月・前の年の同じ月との比べ（差と率） | R-016-6〜8・19・21 |
| 費用 | `/profit/costs/` | 月の費用の一覧と合計。入れる・直す・消す（`invoice.edit` のときだけ）。建物を選ぶと、その建物の契約だけが選べる | R-016-9・10・20・21 |

- 画面の中身は、`apps/web/src/lib/profit/` の純粋な関数と、Supabase を呼ぶ薄い層（`repo.ts`）に分ける。関数は Vitest で確かめる
  - `calc.ts`：行の足し合わせ、3つの切り方での集め方、粗利率、差と率、月の足し引き
  - `format.ts`：種類・月・差の言葉、DB が断った理由の文面
  - `validate.ts`：費用の入力の検査（月・種類・金額・建物と契約の組）
- 月の行は、`profit_monthly` から、今の月・前の月・前の年の同じ月を**一度に**読む（`month in (...)`）。名前（取引先・建物・契約）は、既存の一覧の関数（`listClients`・`listBuildings`・`listContracts`）で引く
- 今の会社は 001 の `useSession` から読む。`amount.read` を持たない人には、数字の代わりに権限がないことを出し、view も費用も読みに行かない。`invoice.edit` を持たない人には、費用の操作を出さない（出し分けのためだけ。判定は DB が行う）
- 費用は、画面から直接書く（RPC を作らない）。DB が断ったときは、DB のコードから日本語の理由を出す。消すときは、確かめの操作（もう1回押す）を挟む

## 8. 決めたこと

| 決めたこと | 理由 | ほかの案 |
|---|---|---|
| 売上は、発行した請求書（発行以降）の明細の税抜の金額。入金の有無では動かない | 発行した請求書は直せない（011）。入金の遅れは粗利と別の話（残高は請求の画面） | 入金済みだけ（現金主義）、税込 |
| 下書きは売上に入れず、別の列（見込み）で出す | 下書きは直る。見込みは見えた方がよいが、粗利には混ぜない | 下書きも売上に入れる、出さない |
| 売上の月は、請求書の請求月 | 毎月請求の契約と、その月の作業・案件が同じ月で並ぶ。作業・案件の月と請求月が違うこともあるが、請求書に載った月が会計の月 | 作業の日・案件の日で月を決める（請求書と合わなくなる） |
| 小口は、確認済み・締め済みの出金だけを費用にする | 確認前の金額は直る。006 の「確認したあとは直せない」と合う | 下書きも入れる（締めるたびに粗利が動く） |
| 小口の出金は、入力した金額のまま足す（税込のことが多い） | 小口には税の列がない。売上との税の合わせ方は、人が決める | 税を分ける（列が要る） |
| 建物のない小口・費用は、「建物なし（共通）」の行にして消さない | 全体の粗利を、どの切り方でも同じにするため（R-016-7） | 建物のないものを除く（合計が合わない） |
| 費用は 月×建物（または契約）に付ける。按分はしない | 要件の範囲。複数の建物にまたがる費用は、人が分けて入れる | 按分の機能 |
| 費用に作業の列を置かない | 012 の表がまだなく、要件の範囲の外。必要なら、012 の取り込みのあとで足す | 列だけ先に置く |
| 費用は画面から直接書く（RPC なし）。直せるのは `invoice.edit`、読めるのは `amount.read` | crud.md の 016 の行。履歴は型 B の既定で付く。業務の決まりは、月の1日・種類・金額の check と、建物と契約の組の RLS で足りる | RPC で作る |
| 費用のある建物は消さない（`has_costs`） | 建物を消すと、過去の粗利が「建物なし」に落ちるのを避ける | 消してよい（履歴が崩れる） |
| view は `security_invoker`。小口の枝にだけ `amount.read` を足す | 見る人の RLS を通すのが基本（指示）。小口は持ち手の本人も読めるので、足さないとスタッフに自分の出金が出る | security definer の view（RLS を迂回する） |
| 前の月・前の年との比べは、画面で出す（差と率）。DB は月の行を返すだけ | 3つの月の行を一度に読めば足りる。率の端数・0 で割る扱いは画面の部品（Vitest）で確かめる | DB の view に前の月の列を持つ（月×4つの結合で遅い） |
| 比べる側が 0 のときは、率を出さない | 0 で割れない。「増えた」とだけ分かればよい | 100% とする（誤解） |
| 遅くなったときの集計の表は、今は作らない | data-model.md「遅くなったら」。まず view と索引で足りるかを見る | 最初から毎晩の集計 |
