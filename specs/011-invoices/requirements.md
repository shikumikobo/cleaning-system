# 機能011：請求（要件）

状態：実装
作成：2026-11-21

全体の言葉と役割は [../product.md](../product.md)、変えない決まりは [../constitution.md](../constitution.md)、表と policy の型は [../data-model.md](../data-model.md)（011 の章、型 B）、CRUD は [../crud.md](../crud.md)（011 の章）。001（権限・番号）・002（取引先）・003（案件の金額）・004（税の計算）・010（契約の中身・作業の金額）・015（お知らせの種類）が前提。

## 1. ねらい

月ごとに、取引先ごとの請求書の下書きを自動で作る。載せるのは、契約の定期の月額、その月に行ったオプションと特別清掃（作業の金額）、終わった案件の金額。同じものを二度請求しない。発行で番号と合計を固定し、税は請求書1枚に1回かけ、インボイス（適格請求書）の書き方で印刷する。送付・取消・入金（一部入金も）の状況を持ち、会計ソフトに渡す CSV を出す。入金の遅れのお知らせを出すのは波 6（ここでは種類があることだけ確かめる）。

## 2. 利用者の話

- 社員として、月を選んでボタンを押すだけで、取引先ごとの請求書の下書きができてほしい。定期の月額も、その月に行った作業の分も、終わった案件の分も入っていてほしい
- 社員として、下書きの品名と数量を直し、不要な明細を外し、期日を決めて、発行したい。発行したら番号と合計が固定されてほしい
- 社員として、請求書を A4 で印刷したい。インボイスの登録番号と、税率ごとの合計が載ってほしい
- 社員として、送った日を記録し、入金（一部でもよい）を記録して、入金済みかどうかが分かってほしい
- 社員として、間違えて出した請求書は取り消し、同じ月の請求書を出し直したい
- 管理者として、会計ソフトに渡す CSV を月ごとに出したい
- スタッフ・外部の人は、請求書を見ない

## 3. 受け入れ基準

### 下書きを作る

- **R-011-1** `invoice.edit` を持つ人が、月（その月の1日に直す）と、取引先（空なら全部）を選んで下書きを作ったとき、システムは、取引先ごとに請求書（状況：下書き）を1枚作り、その月に有効な契約の「毎月請求」の中身を、1つ1つ明細（元：契約の中身 `service_key` と月）にする。金額が 0 の中身は載せない
- **R-011-2** 同じとき、システムは、その月に行われた（状況が完了で、予定の日がその月）契約の作業の金額（`work_charges`）を明細（元：作業）にする。完了していない・取り消した・消した作業、金額が 0、契約を元にしない作業（案件の作業）、ほかの月の作業は載せない
- **R-011-3** 同じとき、システムは、終わった（状況が完了）案件で、請求する（`billable`）金額（`request_charges`）を明細（元：案件）にする。請求しない・金額が 0・完了していない・消した案件は載せない。案件に完了日の列はないので、案件を作った日がその月の末日以前のものを載せる
- **R-011-4** 請求書は、取引先ごとに1枚（建物をまたいで）で、明細の品名に建物の名前を付ける。別の取引先の分は別の請求書にする。取引先ごと・月ごとの請求書（取消を除く）は1枚だけ
- **R-011-5** 同じ月を二度呼んでも、明細は増えない。同じ契約の中身の同じ月、同じ作業、同じ案件は、消していない明細に1つしか載らない（DB の一意の索引でも守る）
- **R-011-6** 月の途中で契約の中身の金額が変わっても日割りにしない。その月の1日に有効な中身の金額で1行（月の途中から始まる中身なら、その月で最初に始まる中身の金額）。月が始まる前に終わった中身と契約は載せない
- **R-011-7** その取引先・月に、すでに発行した（下書きでない）請求書があるとき、システムは下書きを足さず、飛ばした取引先として数えて返す。下書きがあるときは、新しく出てきた元だけを足す
- **R-011-8** 取り消した請求書の月は、下書きを作り直せる。作り直した下書きは、`previous_id` に、その月の取り消した請求書を入れる
- **R-011-9** 月が空ならば断り（`period_required`）、別の会社の取引先・会社ならば、権限がないのと同じ 42501 で断る。載せるものがなければ、何も作らず 0 件を返す

### 下書きの編集と削除

- **R-011-10** 社員が、下書きの請求書の期日・税率・備考と、下書きの明細の品名・数量・単位を直す、明細を外す（論理削除）とき、システムはそれを保存する。明細の金額は、DB が 数量 × 単価（円未満は四捨五入）で出す。数量が 0 以下・品名が空・税率が 0〜1 の外ならば、保存しない
- **R-011-11** 画面や API から直接、請求書を作る・状況・番号・発行日・合計・税・前の版・取消の列を書く・請求書を消す、明細を作る・元（契約の中身・作業・案件）・単価・金額を書く、入金を作る・直す、を、システムは受け付けない（RPC だけが決める）
- **R-011-12** 社員が下書きを消す（RPC）とき、システムは請求書と明細を論理削除する。発行した請求書は消させない。消した下書きの元は、次の下書きに入れ直せる
- **R-011-13** 明細の元は、「契約の中身と月」「作業」「案件」のどれか1つだけ。複数・なしは保存しない

### 発行

- **R-011-14** 社員が下書きを発行したとき、システムは、明細の金額の合計（小計）・税・合計を計算して入れ、番号と発行日（日本時間の今日。指定もできる）を付け、状況を「発行」にする。期日が空ならば、請求月の翌月末にする（それが発行日より前なら、発行日の30日後）
- **R-011-15** 税は、請求書1枚ごとに1回、小計 × 税率で出し、円未満を切り捨てる。合計は 小計 ＋ 税。明細ごとには税をかけない
- **R-011-16** 番号は `I-<西暦>-<4桁の通し番号>`（例 I-2026-0001）で、会社ごと・年ごとに 1 から振る（年は発行日の年）。見積の番号を進めない。同じ番号を2通に付けず、欠番を作らない（発行に失敗したら、番号も進まない）
- **R-011-17** 明細が1つもない・合計が 0・期日が発行日より前・下書きでない（取消）請求書は、システムは発行させず、理由を返す。すでに発行した請求書をもう一度発行したとき、何もしないで前の番号と合計を返す
- **R-011-18** 発行した請求書と、その明細は、システムは直せない・消せない・足せない（RLS で止める。下書きの行だけ直せる）

### 送付と取消

- **R-011-19** 社員が発行した請求書の送付を記録したとき、システムは状況を「送付」にして送った日時を入れる（送るのは人で、システムはメールを送らない）。二度呼んでも同じ。下書き・取消は送付にさせない。入金のあと（一部入金・入金済み）は状況を変えず、断る
- **R-011-20** 社員が発行・送付の請求書を取り消したとき（理由は任意）、システムは状況を「取消」にし、取り消した日時と理由を入れ、明細を消す（元が空くので、同じ月に出し直せる）。番号は残り、ほかの請求書に使い回さない。入金のある請求書・下書きは取り消させない（入金を先に消す／下書きは消す）。二度呼んでも同じ
- **R-011-21** 請求書に載った案件の金額・作業の金額・契約の中身は、直せない。取り消し・下書きを消して載らなくなれば、また直せる

### 入金

- **R-011-22** 社員が発行・送付・一部入金の請求書に入金（入金日・金額・メモ）を記録したとき、システムは、入金の合計が請求の合計に満たなければ「一部入金」、達したら「入金済み」に、同じ処理の中で状況を変える
- **R-011-23** 金額が 0 以下・入金日がない・入金の合計が請求の合計を超える入金は、システムは受け付けない。下書き・取消の請求書には入金させない
- **R-011-24** 入金を直す・消すとき、システムは同じ処理の中で状況を計算し直す（入金済み → 一部入金 → 送付済み、または発行）。直す・消すのは、取り消していない請求書のものだけ
- **R-011-25** 請求書ごとの入金額と残高は、view（見る人の権限で絞る）で読める

### 権限と守り

- **R-011-26** スタッフ・外部の人・運営・ログインしていない人ならば、システムは請求書・明細・入金を読ませず、RPC（下書き・発行・送付・取消・削除・入金）も呼ばせない。`invoice.edit` を持たない人は RPC を呼べない。社員・管理者は、すべてできる
- **R-011-27** `amount.read` を持つ人だけが、請求書・明細・入金を読める
- **R-011-28** 別の会社の請求書・明細・入金は、読めない・直せない・RPC も効かない（RPC は、行が見つからないときと権限がないときを、同じ 42501 で返す）
- **R-011-29** 請求書・明細・入金を作る・直す・消すとき、システムは履歴に残す（001 の変更の履歴。RPC の変更は source が rpc）
- **R-011-30** 請求書（消していないもの。取消も含む）がある取引先は、システムは消さず、理由（`has_invoices`）を返す（002 の `app.usage_refs` の登録が効く）
- **R-011-31** お知らせの種類 `invoice_overdue`（入金の遅れ）が、`notification_kinds` に載っている（015 が初めから登録。波 6 の処理が使う）

### 計算・印刷・CSV

- **R-011-32** 画面の下書きの合計（小計・税・合計）は、DB の発行の RPC が出す合計と、同じテストのデータ（`supabase/tests/fixtures/invoice_totals.json` と DB のテストの同じ数字）で、すべて一致する
- **R-011-33** 請求書は、画面の印刷で A4 に出す。インボイスの書き方として、請求書の番号・発行日・取引の月・宛先・明細（品名・数量・単位・単価・金額）・税率ごとの対象額と消費税・合計・支払期日・発行した会社の名前・住所・電話・登録番号を載せる。登録番号が未登録ならば、その行は出さない。下書きは「下書き」、取消は「取消」の印を付ける
- **R-011-34** 会計ソフトに渡す CSV を、請求書ごとの1行（番号・発行日・支払期日・取引先・請求月・税率・小計・消費税・合計・入金額・残高・状況）と、明細ごとの1行（番号・請求月・取引先・品名・数量・単位・単価・金額・税率）の2つ出せる。文字コードは UTF-8（BOM つき）。区切り・引用符・改行を含む値は引用符で囲み、数式として読まれる先頭の文字は無害にする。下書き・取消は含めない
- **R-011-35** 入金の期日を過ぎて残高がある請求書（発行・送付・一部入金）は「期日超過」と分かる。状況・期日・入金額・残高の見せ方（日本語）と、一覧の絞り込み（番号・取引先の言葉・状況・月）の部品を持つ
- **R-011-36** 請求の一覧・下書きの作成・詳細と下書きの編集・発行・送付・取消・削除・入金の記録（直す・消す）・印刷・CSV を、スマホの幅で使える画面で持つ。`invoice.edit` を持たない人には、作る・直す・出す操作を出さない（出し分けのためだけ。判定は DB が行う）。入力は保存の前に検査し、RPC が断った理由は日本語で出す

## 4. 範囲の外

- 入金の遅れのお知らせを作る処理（波 6。種類 `invoice_overdue` は 015 が登録済み）
- 請求書のメール送付・PDF のファイル保存（PDF は画面の印刷。送付は人が行い、システムは記録だけ）
- 振込先の口座の表示（会社の口座の情報の列がまだない。印刷の備考に書ける）
- 軽減税率（請求書の中で税率が混ざること）。値引きの行（マイナスの単価）
- 銀行の入金データの自動の取り込み・消し込み
- 会計ソフトそのもの

## 5. 決まっていないこと（推奨の案で進める）

| 点 | 推奨 | 理由 |
|---|---|---|
| 契約の途中で金額が変わった月 | 日割りにしない。月の1日に有効な中身の金額。明細の数量（小数 2 桁）を直せば、手で日割りにできる | 行は分けて持つのでどちらにもできる（data-model.md）。自動の日割りは日数の数え方が会社ごとに違う |
| 案件の請求の月 | 案件を作った日が月の末日以前の、まだ載っていない完了済みの案件 | 案件に完了日の列がない。月に縛ると請求し損ねる |
| 作業の金額の月 | 予定の日がその月の完了した作業だけ | 仕様の「その月に行った」。過去の月の取りこぼしは、その月の下書きを作ると入る |
| 期日の初めの値 | 請求月の翌月末 | 月末締め翌月末払いが多い。取引先ごとの支払条件（文字）は読まない |
| 請求書の状況の値 | `draft`・`issued`・`sent`・`partial`・`paid`・`cancelled` | 状況の値は英語の小文字（data-model.md の 6 つ） |
| 請求書の番号の形 | `I-<西暦>-<4桁>` | 会社ごと・年ごとの通し番号（見積と同じ形）。ひと目で請求書と分かる |
| 税の端数 | 請求書ごとに1回、切り捨て | constitution.md |
